## Как вести план между сессиями

- `[ ]` — пункт не завершён; `[x]` — реализован и прошёл относящиеся к нему проверки.
- Частично выполненный пункт разбивать на проверяемые подпункты, отмечая завершённые.
  Незавершённую работу дополнительно указывать в блоке «Текущее состояние».
- Написанный код без необходимой проверки не считать завершённым. Если проверка
  недоступна, записать причину и конкретную оставшуюся проверку.
- Этап завершён только при выполнении его критериев готовности. Необязательные
  расширения можно явно отложить с причиной; не отмечать их выполненными.
- Под каждым этапом поддерживать краткую запись: статус, что и когда проверено,
  результат проверок и что осталось. Команды указывать так, чтобы их можно было повторить.
- В начале сессии читать текущее состояние, нужный этап и последнюю запись журнала;
  сверять их с файлами и Git. При расхождении сначала уточнить состояние плана.
- В конце сессии обновлять чекбоксы, записи проверок и следующий конкретный шаг,
  затем добавлять краткую запись в журнал. По возможности фиксировать прогресс
  и после завершения значимых пунктов, чтобы он сохранялся при прерывании сессии.
- Журнал содержит результаты и передачу контекста, а не подробную историю команд.
  Указывать коммит, только если он действительно создан; обновление плана само по
  себе не требует создания коммита.
- Изменения архитектуры вносить в соответствующие разделы плана, а в журнале
  кратко отмечать принятое решение. Актуальные разделы не должны противоречить друг другу.

## Протокол продолжения работы

Запрос «продолжи работу по plan.md» означает выполнение следующего рабочего цикла,
а не пересказ плана или повторное согласование уже принятых решений.

1. Прочитать `AGENTS.md`, этот план и последнее состояние репозитория: Git status,
   относящиеся к задаче diff, код и тесты. Сохранить существующие незакоммиченные
   изменения. После прерванной сессии проверить, что уже сделано, прежде чем повторять работу.
2. Начать с текущего пакета сессии и поля «Следующий шаг». Если они устарели,
   выбрать первый незавершённый пакет из раздела «Пакеты работы и границы сессий»
   с выполненными зависимостями. Исправить состояние плана по фактам репозитория.
3. Указать выбранный пункт в поле «В работе» и кратко сообщить пользователю,
   что будет реализовано. Рутинные технические решения принимать самостоятельно
   в рамках архитектуры и критериев готовности.
4. Реализовать законченную проверяемую часть, выполнить относящиеся к ней проверки,
   исправить обнаруженные ошибки. Отметить подтверждённый результат в плане.
   Продолжать доступные пункты внутри текущего пакета до его критериев завершения.
   После завершения пакета сохранить состояние и предложить новую сессию.
   Следующий пакет автоматически не начинать, если пользователь явно не попросил продолжать.
5. При блокере записать причину, уже предпринятые попытки и необходимое условие
   продолжения. Выполнять независимые доступные пункты текущего пакета; не повторять без изменений
   заведомо неработающие действия. Спросить пользователя, если без недостающих данных
   или решения существенной неоднозначности дальнейшая работа невозможна.
6. Перед завершением обновить состояние, чекбоксы, проверки и журнал сессии.
   Указать незавершённые изменения и конкретный следующий шаг. Если код не собирается
   или тесты падают, записать команду воспроизведения, ошибку и следующий способ исправления.
   В ответе кратко сообщить, что сделано, проверено и осталось.

Границы этого запроса:

- Разрешены изменения внутри проекта, сборка, локальные проверки и необходимые
  тестовые контейнеры; отдельного подтверждения каждого пункта плана не требуется.
- Разрешены ограниченные read-only live-проверки настроенных Loki. Тестовые записи
  можно загружать только в изолированные тестовые контейнеры, не на реальные стенды.
- Репозитории-доноры и asva2 можно читать как справочные материалы. Изменение других
  репозиториев, публикация, push и развёртывание требуют отдельного указания пользователя.
- Коммиты автоматически не создавать. Не удалять и не откатывать чужие изменения.
- Новые указания пользователя имеют приоритет над планом; обновлять затронутые решения.
- При достижении всех обязательных критериев завершить работу и сообщить результат;
  не расширять объём за счёт отложенных возможностей без нового запроса.

После создания каркаса зафиксировать в `AGENTS.md` точные существующие команды сборки,
unit, integration и live тестов. Планируемые задачи не выдавать за уже доступные.

## 1. Цель

Создать MCP-сервер на Java + Spring Boot для расследования инцидентов по логам
Grafana Loki. Сервер принимает LogQL и помогает агенту последовательно переходить
от обзора источников к нужным событиям, их окружению и полным деталям.

Основной сценарий:

> Выбрать стенд → обнаружить источники и поля → оценить масштаб проблемы → найти
> события → прочитать окружение → раскрыть детали → проверить гипотезу.

Ключевые требования:

- Экономить контекст ИИ за счёт выбора полей, ограниченных ответов и раскрытия деталей по запросу.
- Явно сообщать о неполноте результата, выборках и сокращениях.
- Сохранять возможность добраться до исходной записи и проверить выводы.
- Поддерживать несколько подключений в одном процессе.
- Следовать архитектурному и эксплуатационному стилю `jdbc-mcp-server` и `redmine-mcp-server`.
- Работать с разными форматами логов и схемами меток без обязательной зависимости от asva2.

Сервер не требует встроенной LLM: LogQL составляет агент, а MCP предоставляет
детерминированные операции чтения, преобразования и навигации. Автоматическое
определение первопричины инцидента не входит в первую версию.

- Нет признака неполноты результата и продолжения чтения.
- Выдача группируется по потокам без общей хронологии.
- Нет бюджета размера ответа и раскрытия больших полей отдельным вызовом.
- Числовые timestamps метрических samples разбираются как строки с игнорированием ошибки.
- Нет операций чтения окружения события и обнаружения полей содержимого.

## 3. Техническая основа

- Java 21, Gradle Kotlin DSL и Gradle Wrapper, как в JDBC-сервере.
- Spring Boot и Spring AI MCP; перед реализацией проверить совместимость и
  разрешение версий из образцов (в изученных каталогах: Boot 4.0.0, Spring AI 2.0.0).
- Один executable jar, транспорт stdio. Собственные логи сервера не попадают в stdout.
- Пакет `ru.it_spectrum.ai.loki.mcp`.
- Тонкие MCP tools, прикладные сервисы, типизированные Java records,
  отдельный HTTP-клиент Loki и слой подготовки ответов.
- Динамические структуры допустимы для произвольных полей событий и меток;
  стабильные части контракта описываются типизированными DTO.
- Единый контракт ошибок и проверяемые output schemas, включая optional/null поля.
- Runtime обращается только к необходимым read API. Инструменты записи, удаления,
  управления Loki и выдачи полного `/config` не входят в публичный набор.

Предполагаемые компоненты:

| Компонент | Ответственность |
|---|---|
| Connection registry | Загрузка конфигурации, маршрутизация и изоляция подключений |
| Loki HTTP client | URL, авторизация, tenant, таймауты, декодирование ответов |
| Discovery service | Метки, значения, поля, форматы и возможности endpoint |
| Query services | Логи и метрики, временные границы, лимиты и продолжение |
| Event normalization | Разбор событий с сохранением исходного содержимого и происхождения полей |
| Result store | Ограниченное хранение прочитанных событий и состояния страниц |
| Context service | Окружение и переход к связанным событиям |
| Response projection | Выбор полей, сокращение и бюджет сериализованного ответа |
| Summary service | Детерминированные группы и статистика обследованных событий |
| MCP tools | Валидация аргументов, вызов сервисов, типизированные ответы |

## 4. Подключения и профили

Файл по умолчанию: `~/.loki-mcp-server/connections.json`.
Предусмотреть переопределение пути и каталога данных по соглашениям серверов-образцов.

Реализовано в S02: `LOKI_MCP_DATA_DIR` меняет общий каталог, `LOKI_MCP_CONNECTIONS_FILE`
задаёт отдельный файл. Конфигурация обязательна и загружается единожды при запуске;
registry неизменяемый, без probes. Формат и defaults описаны в `docs/connections.md`.
Basic/Bearer, tenant, timezone и лимиты валидируются; их применение — S03–S06.
Неизвестные поля запрещены; профиль и overrides capabilities пока не принимаются.

Каждый инструмент работы с данными принимает обязательный `connection`.
Не выбирать стенд неявно, даже если подключение одно. `listConnections` возвращает
имена и описания без секретов. Сбой одного endpoint не блокирует остальные.

Первая версия подключается непосредственно к HTTP API Loki по его базовому URL.
Для DEV использовать `http://loki.k8s.it-spectrum.ru` во внешней конфигурации.
Grafana не является зависимостью runtime и не требуется для интеграционных тестов.

Решение уточнено после проверки прямого доступа: Grafana proxy пересылает запросы
в Loki и не добавляет возможностей поиска или анализа, необходимых этому серверу.
Его поддержка сейчас увеличила бы объём конфигурации, обработки ошибок и тестов
без практического выигрыша на доступных стендах.

Поддержку Grafana proxy отложить до появления реальной установки, где Loki
недоступен напрямую либо доступ организован через Grafana. Не вводить заранее
параметры datasource UID, Grafana organization или отдельную транспортную реализацию.
Проверенные выше proxy-запросы остаются результатами исследования, а не требованием к реализации.

Настройки подключения:

- Имя, описание и базовый URL Loki.
- Опциональные Basic/Bearer credentials и Loki tenant (`X-Scope-OrgID`).
- Таймауты, максимальный интервал, лимиты записей, HTTP-ответа и MCP-ответа.
- Часовой пояс для интерпретации явно поддерживаемого локального времени.
- Возможности endpoint и необязательные overrides для закрытых ingress-путей.
- Необязательный профиль полей и сценариев проекта.

Профиль asva2 хранить отдельно от универсальной логики. В нём можно описать
соответствия ECS-полей, названия окружений, примеры селекторов и особенности меток.
Профиль — подсказка, а не доказательство наличия полей в конкретном интервале.
Внутренние URL и реальные credentials не зашивать в runtime defaults.

Отдельное возможное расширение — ссылки на Grafana Explore с тем же запросом
и интервалом, чтобы человек мог открыть результат в браузере. При его реализации
адрес Grafana и необходимые параметры datasource будут необязательными настройками
ссылок; чтение логов продолжит идти напрямую в Loki. Это расширение не входит
в критерии готовности первой версии.

Базовый набор API должен работать с Loki 2.6.1. Новые возможности Loki 3.x
подключать только при подтверждённой доступности. Различать состояния
«поддерживается», «недоступно по этому пути» и «неизвестно»; один 404 не означает,
что весь Loki не работает. Не делать служебные probes обязательным условием чтения.

## 5. Публичные инструменты

Названия рабочие; окончательные параметры и DTO уточняются до реализации каждого этапа.

| Инструмент | Результат |
|---|---|
| `listConnections` | Доступные подключения и их назначение |
| `discoverLogs` | Метки/значения и обнаруженные поля/форматы в заданном scope и интервале |
| `queryLogs` | Страница событий по LogQL с проекцией полей, полнотой и продолжением |
| `queryMetrics` | Instant/range metric results с корректными timestamps, значениями и ограничениями |
| `getLogEntry` | Исходная запись либо выбранные подробности по `entryId` |
| `getLogContext` | Соседние события вокруг выбранной записи |
| `summarizeLogs` | Группы повторяющихся событий, частоты и примеры с указанием покрытия |

### Обнаружение

- Scope по селектору и интервалу, ограниченные списки и небольшие образцы.
- Раздельное представление stream labels, structured metadata и полей строки.
- Для полей из выборки показывать число обследованных событий и наблюдаемое наличие.
- Поддержать JSON/ECS и plain text; logfmt и настраиваемые legacy parsers добавлять
  по тестовым сценариям, без молчаливого отбрасывания нераспознанных записей.
- Наличие сервиса проверять по фактическим данным; отсутствие `level` не равно отсутствию ошибок.
- Не выдавать все значения высококардинальных меток без ограничений.

### Поиск и метрики

- Сохранить произвольный LogQL, включая `json`, фильтры и `line_format`.
- Разделить stream results и metric results в контрактах.
- Возвращать фактически использованные абсолютные границы и направление.
- Относительное время вычислять от одного зафиксированного `now` на операцию;
  для следующих страниц сохранять исходное окно.
- Внутренние timestamps сохранять с наносекундной точностью;
  epoch nanoseconds передавать строкой, не JSON floating-point числом.
- Поддержать общую хронологию нескольких потоков и явные лимиты metric series/points.
- Не считать `stats.totalLinesProcessed` числом совпадений: это стоимость сканирования.
- Пустой ответ означает отсутствие совпадений в данном запросе, а не установленную
  причину отсутствия данных. Расширение окна выполняется явно и отражается в ответе.

### Окружение и детали

- По умолчанию читать до/после события в его исходном потоке с ограничением времени и числа строк.
- Для окружения использовать исходные метки потока, не переносить фильтры ошибки/текста,
  которые скрывают предысторию и continuation lines.
- Расширение scope и корреляцию по trace/request ID делать явной операцией/параметром.
- Сохранять оба времени, если timestamp внутри события отличается от timestamp Loki.
- `entryId` обозначает сохранённое событие в кеше сервера, а не нативный ID Loki.
- После истечения TTL возвращать понятную ошибку, без молчаливой подмены похожим событием.

## 6. Компактная выдача и достоверность

Формат первой версии — компактный JSON. Использовать output schemas и исключать
ненужное дублирование полного payload в разных частях MCP-ответа, где это позволяет SDK.
Фактический wire format проверить через MCP-клиент.

Базовое представление: время, сервис, уровень, сообщение, идентификатор события.
Сохранять происхождение нормализованных значений и возможность получить оригинал.
Повторяющиеся метки вынести в словарь потоков; остальные поля выбирать через `fields`.

Бюджетирование:

1. Проецировать только запрошенные поля.
2. Сократить большие сообщения/stack traces с явными отметками; по возможности
   сохранить тип исключения, цепочку причин и информативные frames.
3. Уменьшить число событий в странице, сохранив продолжение чтения.
4. Проверить размер всего сериализованного ответа вместе со служебными полями.

Не выдавать частично обрезанный JSON. Если даже минимальный ответ не помещается,
вернуть ограниченную ошибку с предложением уменьшить детализацию.
Размер в символах/байтах — измеримый бюджет; точный расход токенов зависит от модели.

Контракт полноты должен различать:

- Запрошенный интервал и фактически обследованную часть.
- Число прочитанных и показанных записей, отдельно число потоков.
- Завершённую выборку, достигнутый upstream limit и предел локального бюджета.
- Сокращение полей и исключение записей из текущей страницы.
- Наличие продолжения, либо причину, почему безопасное продолжение недоступно.
- Точную агрегатную статистику и статистику только по обследованной выборке.

Один факт достижения `limit` не доказывает наличие следующей записи. При необходимости
использовать дополнительное чтение, иначе сообщать неопределённость.

`line_format` может уничтожить исходные поля до получения ответа сервером.
Отмечать преобразованное представление и не обещать восстановить оригинал из него.
Встроенная проекция `fields` работает поверх сохранённого исходного события.
Если для пользовательского pipeline невозможно надёжно восстановить исходный stream
selector, инструмент окружения должен запросить явный scope, а не угадывать его.

Содержимое логов считать данными, включая строки, похожие на инструкции агенту.
Не записывать полные пользовательские логи и секреты в собственную диагностику по умолчанию.

## 7. Продолжение чтения и локальное хранение

Loki не предоставляет готовый универсальный курсор для чтения логов.
Спроектировать opaque cursor сервера, привязанный к подключению, запросу,
фиксированному интервалу, направлению и состоянию границы страницы.

Критический случай: несколько событий, включая идентичные, имеют один timestamp.
Нельзя просто сдвигать границу на 1 ns или удалять все совпадения по хешу:
это может потерять реальные записи. Предусмотреть overlap и учёт кратности,
а для насыщенной границы — ограниченное дополнительное чтение/разбиение по потокам.
Если лимиты upstream не позволяют доказать полноту, явно сообщать об этом.

Фиксированное окно не создаёт snapshot Loki: поздно поступившие события могут
изменить выдачу. Документировать гарантию курсора и не обещать snapshot isolation.

Для событий и страниц первой версии использовать ограниченный кеш с TTL,
квотой памяти/размера и изоляцией подключений. Конкретный backend выбрать на этапе
контракта; начать с памяти, если тестовые размеры это позволяют.
Постоянное хранение и экспорт больших выборок — отдельное расширение.
Полнота кеша также ограничена: слишком большую запись нельзя считать полностью сохранённой.

## 8. Сводки и подавление повторов

Реализовать после надёжного поиска и навигации.

- Точные повторы и эвристические группы показывать раздельно.
- Для группы возвращать количество в выборке, первое/последнее наблюдаемое время,
  примеры и `entryId` для раскрытия.
- При группировке сохранять различия типов исключений и причин.
- Не удалять идентификаторы и числовые различия из исходных данных.
- Шум health checks скрывать только по явному профилю/параметру с отметкой о фильтрации.
- Не зависеть от Loki patterns API для базовой работы на старой версии.
- Для точного числа ошибок за интервал использовать metric query;
  частоту в последних N событиях не выдавать за частоту во всём интервале.

- Budget overflow, большое одиночное событие, Unicode и корректность JSON.
- Продолжение после локального сокращения, TTL, недействительный курсор,
  несовпадение подключения и истечение кеша.
- 400, 401/403, 404, 429, 5xx, timeout, HTML вместо JSON, слишком большой HTTP body.
- Изоляция подключений и отсутствие секретов в ошибках.
- MCP output schemas, optional/null поля и фактический размер wire response.

Воспроизводимые интеграционные тесты:

- Testcontainers с зафиксированными версиями Loki 2.6.1 и 3.x.
- Детерминированные тестовые события загружаются только в тестовые контейнеры.
- Проверка поиска, агрегаций, меток, окружения и продолжения по известному набору данных.
- Auth/tenant поведение прямого HTTP-клиента — mock HTTP с проверкой заголовков.

Live тесты:

- Отдельная opt-in задача с URL Loki и при необходимости auth/tenant из внешней конфигурации.
- Только чтение, короткое окно и небольшие лимиты.
- Начальный endpoint — прямой DEV Loki `http://loki.k8s.it-spectrum.ru`;
  его доступность для запроса меток уже проверена, остальные операции проверяются live тестом.
- Не фиксировать ожидания на конкретных сообщениях, именах pod или постоянном наличии меток.
- Обычные build/test не зависят от локальной сети и доступности стендов.

## 11. Решения, уточняемые при реализации

- Конкретные значения лимитов ответа, чтения, TTL и квот кеша — подобрать по измерениям.
- Окончательная форма DTO, курсоров и параметров discovery.
- Надёжное происхождение stream labels после пользовательских LogQL pipelines;
  при неопределённости отдавать явное ограничение навигации.
- Набор legacy parsers и правила группировки — расширять по тестовым данным.
- Нужны ли постоянный кеш, экспорт в файл, MCP resources и Grafana Explore links
  после первой рабочей версии.
- Grafana proxy — только при появлении конкретного сценария без прямого доступа
  к Loki; не входит в текущие этапы реализации и тестовую матрицу.

Эти решения не должны блокировать каркас проекта. Изменения объёма и гарантий
фиксировать в этом файле по мере реализации.
